# Project AI Environment

이 디렉터리는 프로젝트 로컬 AI 하네스의 실행 계약이다. 제품 요구사항은 `docs/`, 에이전트 공통 규칙은 `AGENTS.md`, 공유 용어는 `CONTEXT.md`, 재사용 스킬은 `.agents/skills/`가 소유한다.

## 작업 시작 순서

1. `AGENTS.md`에서 절대 규칙과 검증 명령을 확인한다.
2. `CONTEXT.md`와 제품 기준 문서에서 용어와 범위를 확인한다.
3. `.ai/GRAPHS.md`에서 작업 노드와 승인 경계를 확인한다.
4. `.ai/LOOPS.md`에서 현재 작업에 맞는 루프를 선택한다.
5. `.ai/templates/work-item.md`로 독립적인 작업 항목을 만든다.
6. 작업 항목의 `Agent rules impact`에서 `AGENTS.md` 영향 여부와 근거를 기록한다.
7. 코드가 바뀐 작업은 그래프를 build/update하고 영향 분석 결과를 작업 항목에 기록한다.
8. 완료 조건과 `AGENTS.md` 최신성을 검증하고 실행한 명령과 결과를 작업 항목에 기록한다.

## 불변 원칙

- 에이전트는 목표, 승인 기준, 테스트 기준을 스스로 완화하지 않는다.
- 제품 범위, 보안 정책, 사용자 승인, held-out 검증은 최적화 대상이 아닌 고정 앵커다.
- 한 번의 구현 루프는 하나의 독립적인 작업 항목만 완료한다.
- 코드 변경은 결정론적 도구의 검증 결과로 종료한다. 모델의 자기평가만으로 완료하지 않는다.
- 하네스 개선은 기능 작업과 분리하고, 한 번에 한 요소만 바꾼다.
- 기준 문서·승인 경계·기술 결정·실제 검증 명령이 바뀌면 같은 작업의 문서 동기화 단계에서 `AGENTS.md`를 확인한다.
- 애플리케이션 코드 변경은 최신 `code-review-graph` 영향 분석을 거치며, 그래프는 테스트와 명세를 대체하지 않는다.
- 외부 시스템 변경, 배포, 삭제, 비용 발생 작업에는 사람의 명시적 승인을 요구한다.

## 상태 모델

`proposed → ready → active → verify → done`

- `blocked`: 권한, 결정, 외부 상태가 없어 진행할 수 없음
- `rejected`: 범위 또는 품질 기준에 맞지 않아 폐기

상태 전이는 `.ai/templates/work-item.md`의 증거 필드를 채운 뒤 수행한다.

## 구성 파일

- `harness.yaml`: 하네스 구성과 고정 앵커
- `GRAPHS.md`: 작업 그래프와 개선 그래프
- `LOOPS.md`: 반복 가능한 개발 루프 명세
- `templates/`: 작업, 인수인계, 평가 템플릿
- `work/`: 활성 작업 항목과 의존 관계

사람을 위한 전체 설명과 다른 프로젝트 적용 방법은 `docs/AI_ENVIRONMENT.md`를 따른다.
